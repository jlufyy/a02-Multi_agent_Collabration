## 1. 交付结论与执行边界

前后端已组成同源运行的本机应用：页面和真实 API 由同一个 FastAPI 实例提供，前端不连接契约测试桩；已接入根目录现有 DeepSeek 配置。浏览器实际完成了需求解析、北京一日行程展示、保存和刷新读回。

**完整业务验收未通过。** 本次实际发现了编辑提交、远距离步行规划、附近地点加入、定位判定、提醒过期、地图配置及默认内容供应商等问题。按用户“遇到问题暂时不用修改”的要求，保留业务实现原状；本轮只完成整合运行所必需的配置、入口与打包改动，并记录问题和建议。不要把“应用启动成功”“基础测试通过”或“响应符合 schema”解释为全功能真实可用。

本轮没有改写根目录 `.env`，没有把模型 Key 或高德 Web Service Key 注入前端，没有操作 ECS 或发布公网服务。前端既有页面、store 和定位算法源码未作业务修复。

## 4. 已确认问题与建议方案

优先级：P1 表示阻塞主要业务或导致位置/提醒错误，应在完整验收前处理；P2 表示展示或规划质量问题。本节所有问题均未修复。

### TF-01 · P1 · 初次保存覆盖已解析地点，后续编辑无法提交

**证据：真实浏览器 + 服务端提案。** 测试行程 `trip_9c7c8a0643564fe9` 的“天坛公园、故宫博物院、故宫博物院-养心殿”已生成并保存。提出“把天坛公园从 90 分钟改为 100 分钟，其余不变”，后端成功返回提案，页面却出现 `MUST_VISIT_UNRESOLVED:天坛公园`，按钮为禁用的“无法应用（存在冲突）”。

**原因：** `PlanningPage.tsx:48` 调用 `projectRequirements(r.plan, req)`；`tripStore.ts:112` 又用传入的原始 requirements 覆盖 plan.requirements。后端 research 已匹配的 `mustVisit[].place` 被原始仅含 query 的需求替换。后端最终校验将未匹配的必去地点视为阻塞项，行为符合其规则。

**建议：** 以返回计划中的 resolved requirements 作为正式计划需求，单独保存用户原始输入作草稿/追溯；保存时校验顶层投影一致性及 intents 绑定，不要用旧草稿覆盖新事实。若用户改变需求，应重新解析/匹配再生成候选。

**复测：** 输入包含未绑定 query 的必去地点 → 生成 → 保存 → 刷新 → 修改时长 → 预览 → 最终复核 → 提交 → 撤销/重做；每步保留相同 POI 绑定，revision 正确递增。

### TF-02 · P1 · 远距离步行导致跨日排程异常，而非可读的不可行报告

**证据：真实 HTTP，两次复现 + 单独诊断。** 北京一日、09:00–18:00、纯步行、历史文化、不指定必去地点。研究选出“八达岭长城、故宫博物院-交泰殿、故宫博物院-养心殿”；首段 67,001 米、893.35 分钟。`live-plan` 返回 FAILED / `INTERNAL_ERROR`，首次 trace 为 `cb11c19c47e14d31a0ad1c8f4fc19a97`，复现 trace 为 `854b1a8bbe394730a1692f45da62db11`。

**原因：** `workflows.py:203` 在路线回填后调用 `planning.py:175` 的 reschedule。下游活动被推到次日，`schemas.py:322` 的日期/dayIndex 一致性验证先抛出 ValidationError，A5 尚未来得及输出可行性报告。诊断安全错误为 `activity dayIndex/date mismatch`。

**建议：** 在 A4 重新排程时检查当日窗口和结束日期；无法安置的可选活动进入有界删减/重排，不越过硬窗口继续构造无效 TripState。必去或锁定条件无法满足时返回明确 INFEASIBLE。候选研究增加真实路网聚类/距离约束，但不要通过虚构路线或缩短交通时间解决。

**复测：** 固定上述真实路线快照进行离线回归，再跑同条件真实地图查询；都应返回合法、可解释的候选或不可行报告，不能返回 INTERNAL_ERROR。另覆盖末日跨日、锁定活动与跨城输入。

### TF-03 · P1 · “附近地点加入行程”使用 UTC endAt，被后端拒绝

**证据：静态路径核对 + 实际 HTTP 422。** `AIPanel.tsx:92` 用 `toISOString()` 构造 endAt，生成 `...Z`；startAt 仍来自计划的 `+08:00` 字符串。按同一形状提交 ADD，请求返回 `VALIDATION_ERROR`，fieldPath 为 `operations.0.ADD.activity.endAt`，原因 `plan time must have +08:00 offset`。

**建议：** 统一计划时间序列化函数，显式转换 Asia/Shanghai 并保留 `+08:00`。不要直接替换字符串尾部 Z；必须保持同一时刻和正确日期。前端共享 schema 增加计划时间约束以便提交前发现错误。

**复测：** 周边真实搜索 → 加入 → 预览 → 最终复核 → 提交；覆盖 23 点附近的跨日活动，确保前后端同样拒绝不合法日程。

### TF-04 · P1 · 前端定位状态机对重复样本重复计数

**证据：SYNTHETIC 确定性复现，非实地 GPS。** 使用服务返回的 GeoPolicy（90 秒驻留、最少 3 个有效样本），输入 t=0 的 sample one、t=90 的 sample two，再重复同一个 sample two。只有 2 个唯一样本却触发 ARRIVE。

**原因：** 前端 `packages/context-engine/src/geo.ts:142` 直接累加 insideSamples，未按 sampleId 去重。浏览器实际导入这份 TS 实现；根目录 ESM 包的去重测试通过，不能替代它。

**建议：** 先统一活动中的定位引擎实现/适配层，再加入有界 sampleId 去重、单调时间校验及跨来源隔离；重复和乱序样本都不能增加驻留计数。

**复测：** 直接运行本轮探针，再覆盖重复、乱序、同时间戳不同 ID、重访、REAL/DEMO 分离；到达必须满足独立有效样本数。

### TF-05 · P1 · 低精度样本没有中断驻留累计

**证据：SYNTHETIC 确定性复现。** t=0 有效位置 → t=30 精度 600 米 → t=60 有效 → t=90 有效。前端仍在 t=90 触发 ARRIVE，跨越了无法证明持续驻留的低精度区间。

**原因：** `geo.ts:112` 的 LOW_ACCURACY 分支只增加 anomalies 并返回，未清除 candidateSince、insideSamples 等候选状态。

**建议：** 不合格精度中断驻留/离开候选；根据既有进度表达 LOCATION_UNKNOWN 或待确认，并等待新的一段有效驻留。不回填缺失轨迹。

**复测：** 低精度分别出现在到达前、离开前、页面恢复后；均不能把低精度之前的驻留累计到之后。

### TF-06 · P1 · 提醒最终显示检查忽略版本和排队时效

**证据：SYNTHETIC 确定性复现。** 队列卡片基于 revision=1，当前 revision=2，排队已 1 小时，只要活动 ID 仍存在，`checkShow` 仍返回 `{ok:true}`。

**原因：** 前端 `notify.ts:27` 接受 ctx.currentRevision，但函数没有使用它；也未核验排队年龄、当前仍在该地点或 arrivalId 是否仍适用。请求完成时的一次版本比较不能覆盖之后的排队等待期。

**建议：** 显示前重新核对 trip/revision/executionMode/demoRunId、活动与意图适用性、arrivalId/当前定位、业务时效及提醒策略；不适用的普通卡片丢弃，需更新风险的重新评估。不要仅凭活动还存在就展示旧内容。

**复测：** 卡片排队时修改/撤销行程、退出演示、离开地点、时间过期；旧卡均不能展示。此探针只证明版本/时效问题，不宣称已完整复现所有跨工作区风险。

### TF-07 · P1 配置缺口 · 地图底图不可用

**证据：实际浏览器。** 页面显示“地图未配置 · 行程仍可编辑”，没有地图底图。后端高德搜索、路线均已成功；这不能证明地图 JS SDK 可用。

**原因：** 根目录仅提供高德 Web Service Key，`MapView.tsx:9` 读取的 `VITE_AMAP_KEY` 等 JS 配置缺失。两类凭证不能直接替换。

**建议：** 取得应用匹配的 JS API Key、安全配置及域名授权；按前端 `.env.example` 设置后重新构建。若采用 serviceHost，应先提供真实安全代理。不要将后端 Key 注入网页来绕过配置问题。

**复测：** 实际浏览器加载地图、真实 POI 标记、服务返回的路线几何、选择联动和当前位置；确认未绘制起终点直线冒充路线，再做 HTTPS 与真机测试。

### TF-08 · P2 · 交通分钟显示长小数

**证据：实际浏览器。** 顶部交通汇总为 `1小时25.766666666666666分`，路段为 `4.766666666666667分钟`。

**原因：** 后端正确保留供应商秒换算的浮点分钟，`ui.tsx:122` 的 fmtMin 直接拼接小数和取模结果。

**建议：** 显示层统一按选定口径取整（面向行程可向上取整）；底层数值继续保留原始精度，避免 UI 格式化影响排程与校验。

**复测：** 0、0.5、4.7667、59.9、60、85.7667 分钟及多路段汇总；分钟显示长度有限且不会出现“1小时60分”。

### TF-09 · P1 可靠性 · 当前默认 A7 内容请求超时

**证据：真实调用。** AIPing / Qwen3.8-27B 生成 80 字游览提示，任务约 130.22 秒终态 FAILED，错误 `LLM_TIMEOUT`，trace `6e661f1252704aaf960d73d5bb8af8ea`。本轮 `contentGenerated=false`。上一轮后端成功记录属于历史，不能覆盖本次失败。

**边界：** 证据说明该次请求超时，不能据此断言供应商永久不可用；也尚不能区分其排队、网络或该型号处理时延。

**建议：** 分别验证所选供应商的时延与模型健康，记录阶段耗时和重试结果；按 SLO 设置 token、超时和总任务预算。需要备用路由时显式配置并向用户显示实际供应商/型号，不静默降级到测试数据。可对 DeepSeek A7 路由进行独立真实验收后再决定是否替换默认值。

**复测：** 讲解、讲稿、清单和内容完善分别进行有界真实请求，记录 p50/p95 与失败率；验证取消、重试、失败后行程保留和双供应商的实际成功证据。本轮没有为“通过验收”而调高时限或更换默认供应商。

### TF-10 · P2 质量建议 · 母景点与内部子景点可能重复占用独立时段

**证据：真实计划观察。** 同一天把“故宫博物院”和“故宫博物院-养心殿”分别作为 90 分钟活动；另一组候选包含“交泰殿”和“养心殿”。这是规划质量风险，不等于这些子景点不能独立游览。

**建议：** 在可获得可信父子关系和用户偏好的条件下，按同一景区归组；内部游览点可作为母景点子任务，或明确说明独立安排的理由。不要只按名称包含关系粗暴删除用户必去点。

**复测：** 故宫、天坛等景区的母子 POI，显式用户要求独立游览与普通推荐两种情况；时间和费用不重复计算。

### TF-11 · P1 体验改进 · 长需求确认表单应改为主 Agent 多轮澄清与 AI 预填

**证据与来源：用户实际体验反馈 + 当前页面实现核对。** 用户输入自然语言后，`InputPage.parse()` 保存抽取结果并跳转 `/confirm`，`ConfirmPage` 展示较长的需求确认表单。当前已有 AI 抽取和部分预填，但用户仍要面对多个字段、地点匹配及高级约束，理解和核对成本较高。本项是用户明确提出的体验改进要求，尚未进行完成率或耗时的可用性统计；本轮仅补充建议，没有修改页面。

**问题：** 目前 AI 主要承担一次性信息抽取，后续补齐、消歧与确认较多地交给用户填表。用户希望借助 AI 减少填表量，应该由支持多轮对话的主 Agent 持续理解需求，在拿不准时提出简短问题，并把回答同步到结构化需求草稿。用户的主要操作应是表达、选择和简要核对。

**建议交互流程：** 自然语言描述 → 主 Agent 分析并预填草稿 → 针对关键缺失或歧义提出少量问题 → 用户回答后增量更新 → 展示简短行程需求摘要 → 用户确认并开始规划。完整表单保留为可选的“查看/高级编辑”入口，默认不展开。

具体建议：

1. **AI 先做分析和预填。** 根据用户描述提取目的地、出行时间/天数、人数、预算、同行需求、交通偏好和感兴趣的景点；结合时间、体力和偏好给出可解释的交通方式与景点建议。已明确表达的信息直接填写，不要求用户再次逐项输入。用户一次补充多个条件时，应一次吸收并更新相应字段。
2. **主 Agent 只追问影响规划的关键问题。** 类似 Codex 的澄清方式，提供简短问题、少量可选答案及自由输入；优先询问会改变方案的日期、目的地、出行方式或硬约束。每轮以 1–2 个关键问题为目标，避免把长表单拆成同样冗长的问卷；可选信息提供“暂不确定/由你推荐”，不必全部问齐才能规划。
3. **区分明确事实、推断和建议。** 用户明确给出的日期和要求可直接预填；相对时间按 Asia/Shanghai 解析并显示具体日期；有歧义的时间应短问确认。AI 推断的日期、人数、预算或交通偏好需标注“待确认/建议”，不能默认为用户已确认。推荐景点应经过真实地点检索，默认作为可调整候选，不能擅自成为“必去”硬约束；营业、票价和预约状态仍须依证据展示。
4. **支持多轮上下文与纠正。** 用户可直接说“改成周日”“我们一共三个人”“不去故宫了”，主 Agent 应保留其它已确认信息，更新受影响字段并简要说明变化。遇到冲突先澄清，避免重复询问已回答的问题；刷新后应能恢复需求草稿和必要的对话上下文。
5. **最终确认采用摘要卡片。** 默认只显示目的地、日期/天数、同行人数、交通方案、预算口径和关键偏好/约束，以简短卡片或标签呈现；用户可点击某项修改，也可继续用自然语言纠正。一键确认整体摘要后再将需求标记为 confirmed，既减少核对负担，也保留用户对关键决定的控制。
6. **实现时沿用结构化契约。** 主 Agent 在多轮对话中维护同一份 requirements 草稿，记录字段来源、待确认项和已回答问题；只有确实缺少生成计划所必需的信息时才阻塞。前端展示对话和摘要，后端继续校验结构、地点身份与硬约束。保留用户原始表达和已解析结果的对应关系，并与 TF-01 的“原始草稿覆盖已解析地点”问题一起设计，避免对话更新再次丢失 POI 绑定。

**示例：** 用户说“想和朋友去杭州玩两天，轻松一点，少走路，看看风景”。主 Agent 可先预填杭州、2 天、低步行强度，并推荐公共交通/打车结合及经过检索的景点候选；接着只问“准备哪两天出发？你们一共几个人？”用户回答后展示摘要，预算可标“未指定”，其余偏好允许后续调整。不要先让用户自行找到并填写整张表。

**复测与验收建议：**

- 信息已充分的输入可直接看到预填摘要并确认，不强制展开完整表单；缺少关键条件时只展示相关追问。
- 多轮回答、一次回答多个问题、临时改期、交通方式纠正和景点替换均正确更新草稿，且不重复询问已确定信息。
- 推断值与用户明确值有可见区别，模糊日期、同名地点及硬约束冲突不会被静默确认为事实；用户可接受、修改或拒绝推荐。
- 手机端完成需求确认时，无需滚动遍历长表单；完整表单仍可按需打开，用户能回到对话继续补充。
- 对比改造前后的确认耗时、手动填写字段数、澄清轮数、返回修改率和放弃率，以真实可用性测试衡量收益，不预先宣称具体提升比例。

### TF-12 · 多 Agent 优化与创新建议 · 主 Agent 统筹、受限协作与简化确认

**性质与边界：** 本节为后续产品与架构建议，尚未实现或完成效果验证，不计入本轮已通过的测试。用户明确要求简化“可确认、可撤销”的交互，避免每个 Agent、每个步骤都要求确认。现有的规划/审核职责分离、修改预览、用户确认和本地撤销机制可作为基础，不必另建一套复杂系统。

#### 方向一：主 Agent 对话统筹，扩展现有 A1

与 TF-11 合并设计：主 Agent 负责对话上下文、问题优先级、摘要和用户选择；现有 A1 负责每轮输入的意图识别、字段提取、缺失/冲突分析与建议追问。景点、交通、规划、审核、主动服务和内容生成继续交给各自专职 Agent。不再增加职责重复的“意图分析 Agent”，也不让用户分别与多个 Agent 对话。

**用户价值：** 一次表达能被持续理解，只补充关键缺失信息，减少填表及重复说明。

**验收建议：** 连续补充、纠正或临时改变要求后，主 Agent 能保持已确认上下文；A1 只更新相关字段，必要时短问澄清；内部 Agent 切换不增加用户操作。

#### 方向二：Agent 在后台解决冲突，只把必要取舍交给用户

交通 Agent 给出真实路线和时长，规划 Agent 提出调整方案，审核 Agent 检查必去、预约、预算等约束；主 Agent 汇总为少量可执行选项。例如发现步行过远，后台先比较“改乘公交”和“替换可选景点”，再用一句话解释取舍。保留锁定及已预约安排，不能为了达成一致擅自放宽硬约束。

采用有界协作：先复用现有结果，最多进行少量修订；只在受影响的职责之间协作，不启动所有 Agent 反复讨论。已知证据不足或约束无法满足时直接说明并询问用户，不靠无限重试。

**用户价值：** 看见清楚的选择及原因，减少人工排查 Agent 之间矛盾的负担。

**验收建议：** “步行太远但必须去某景点”“预算与预约冲突”等输入可得到有限且满足硬约束的备选；无解时明确指出取舍，调用次数和总时延有上限。

#### 方向三：按变化局部重规划，保留已完成和受保护安排

用户说“我累了”“晚到了半小时”“下午想少走路”时，先识别受影响的活动及路线，复用仍适用的结果，只重新查询/计算相关部分，并审核变化对后续安排的影响。保留已完成、已预约和锁定活动；变化扩散到其它时段时要说明。不能把局部计算直接等同于全局可行。

**用户价值：** 保留行程连续性，并有机会减少重复调用和等待。性能改善需要测量，不预先承诺降低比例。

**验收建议：** 对同一需求比较局部更新与完整重规划的结果、调用量及耗时；受保护活动不变，变化后仍通过必要的行程校验，过期数据按需重新核验。

#### 方向四：建议可追溯，按需解释证据和取舍

主 Agent 默认用一句话说明“为什么这样调整”，区分用户要求、真实地图结果、模型建议和未核实信息；用户展开“依据”才查看来源、时间及不确定性。Agent 存在分歧时，说明对方案有影响的原因和取舍，不展示冗长的内部推理、Agent 通信记录或原始模型输出。

**用户价值：** 既能理解和判断建议，也无需阅读完整技术过程。现有字段级 Evidence、独立审核和来源状态是可继续发展的项目亮点。

**验收建议：** “为什么换掉这个景点”“为什么建议坐车”能得到与实际路线/约束一致的短解释；未知营业时间、票价等不会被包装成确定事实。

#### 统一采用简化的确认与撤销设计

**基本原则：后台校验保持必要强度，用户确认按一次完整决策合并。** Agent 调用、检索、重试和内部审核都不是独立确认点；用户也不需要为每次字段抽取或追问回答再点击一次“确认”。

| 场景 | 建议用户交互 | 撤销方式 |
|---|---|---|
| 聊天、查看讲解、搜索候选、表达偏好 | 直接响应或更新草稿，不弹确认窗 | 通过继续对话纠正草稿；不产生正式行程撤销步骤 |
| 初次规划 | 按 TF-11 合并展示简短需求摘要，一次确认后开始；结果只提示关键未核验项，避免再次逐项核对相同内容 | 尚未采用的候选可重新生成；采用后以整份计划为单位管理 |
| 用户已明确指定、无歧义且不涉及受保护安排的小调整 | 必要校验通过后可直接应用，显示简短“已调整，撤销”入口；例如在可行窗口内把某站延长 10 分钟，不再重复询问同一意图 | 撤销整次用户请求对应的修改，不逐条撤销内部计算 |
| AI 主动建议、语义不明确、替换/删除景点、改变日期或预算硬条件、影响预约等重要变更 | 一张简短影响摘要，必要时提供 2–3 个选项；用户选择并确认一次，后台完成最终复核与提交 | 将本次成组变更作为一个撤销单元 |
| 风险提示和到达事实 | 展示提示，不要求确认“Agent 是否可以分析”；推断错误提供“纠正状态”入口 | 事实记录不随计划撤销；用户纠正另行记录 |

小调整的直接应用是**未来设计建议**，并非当前已经支持。它仍须满足请求语义明确、版本一致、无硬约束冲突和无新增阻塞未知项；超出条件时回到一次摘要确认。用户要求的变动若引起明显连锁影响，也应先说明，不能仅按操作类型判断为“小调整”。

**实现简化建议：** 统一由主 Agent 输出“直接答复/更新草稿/直接应用小调整/需要一次选择确认”四类结果；底层复用既有 propose、validate 和本地原子提交，不增加 Agent 专属确认页面。一次用户请求产生的多个活动修改按同一个事务提交与撤销，前端主要保留“撤销上次调整”入口，重做等能力可放入次级入口。最终复核发现数据变化或版本过期时，才重新展示变更摘要，不循环询问未变化内容。

**不承诺撤销外部现实行为：** 本地计划撤销只恢复行程安排，不撤销实际到达、已展示提醒或未来可能发生的购票/预约行为；若后续接入交易，应另行设计外部操作的确认与取消流程，不混入当前轻量计划撤销。

**简化设计的验收标准：** 一次多活动调整最多出现一个必要的用户确认环节；普通对话和内部协作不弹确认；语义明确的小调整可一次完成且能整体撤销；重要取舍清楚可见。撤销后计划约束和版本仍一致，真实事实不回滚。分别记录确认次数、完成耗时、误改率、撤销成功率及模型调用量，验证简化交互没有牺牲正确性。

**建议落地顺序：** 先完成 TF-11 的主 Agent + A1 多轮需求收集，并统一摘要/撤销入口；再增加局部重规划和短证据解释；最后在有实测需求时引入有界冲突协作。避免一次性增加多个新 Agent、复杂协商协议及多层审批界面。

## 5. 静态审查提醒与尚未验证项

1. **生成内容持久化风险（静态发现，未以成功内容在浏览器复现）。** `AIPanel.explain()` 只将响应加入组件 msgs，没有调用 store.putContents；生成内容可能在关闭/刷新后无法恢复。建议先明确聊天临时内容与已保存材料的产品语义，再补充有版本范围的持久化和刷新验收。本轮 A7 请求超时，不能把这项写成浏览器已复现。
2. **配置就绪不等于在线可用。** health/capabilities 的 available 仅反映 Key/型号存在；本轮 health=OK 与 A7 超时同时成立。建议产品文案区分“已配置”“最近请求成功”和“当前请求失败”。
3. **两份契约、两份引擎持续维护风险。** 当前真实响应能通过前端 Zod 校验，但前后端契约并非从同一个源生成；本轮也证明定位行为存在差异。建议逐步生成统一契约并保留前端运行时验证，再用适配层统一引擎接口，避免直接替换导致本地持久化不兼容。
4. **来源迁移和导出。** IndexedDB 按 origin 隔离，目前 UI 未提供完整导入导出迁移入口。固定使用同一地址，后续应增加本地备份/迁移与 schema 迁移验收。
5. **环境警告。** pytest 显示 httpx/Starlette TestClient 的弃用警告；首次默认临时目录清理受本机权限影响，最终改用工作区 basetemp 后测试完成。依赖安装有 ESLint 版本和 Rollup 注释提示；没有在本轮升级依赖。它们不等同于已确认业务失败。
6. 高德营业时间、门票、预约与拍摄许可仍有 UNKNOWN，前端可观察。不能把 POI 真实存在或路线预测当作这些事实已核实。

## 6. 建议处理顺序与验收门槛

1. 先处理 TF-01 / TF-02 / TF-03，恢复“生成 → 保存 → 修改预览 → 最终复核 → 提交”的闭环；补上跨日、锁定与真实路线边界测试。
2. 统一定位和提醒逻辑，处理 TF-04 / TF-05 / TF-06，将本轮探针转为针对实际前端引擎的回归检查。
3. 完成地图 JS 配置及 A7 的真实成功验收，再处理展示和景区归组质量。
4. 按 TF-11 优先重做需求收集体验：主 Agent 多轮澄清、AI 预填和摘要确认，完整表单改为可选高级入口；与 TF-01 同步核对草稿、已解析地点和用户确认状态的保存语义。
5. 按 TF-12 分阶段优化多 Agent 协作，优先复用 A1 和既有校验/提交路径；把确认合并到用户决策层，撤销按整次修改处理，再验证局部重规划与有界冲突协作的收益。
6. 最后在 HTTPS、Android/iOS 真机完成前台定位、权限拒绝、后台恢复、真实到达/离开与 DEMO 隔离验收，并单独验证 Docker、公网服务和重启后的行为。

只有关键闭环通过、已确认 P1 得到解决、外部服务确实成功、真机证据齐全之后，才适合将状态改为“完整可用并验收通过”。本报告交付时仍为“整合完成，问题待修复”。
